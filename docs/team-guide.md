# RMA Editorial Checker — Reviewer Guide

**URL:** `https://rma.xpert.chat` | **Password:** ask Sharad

This guide is for the 2 people reviewing the editorial checker's output. Read it once before you start. It explains what we're building, why your review matters, and how to use each screen.

---

## Why this exists

Today, when a customer books an ad, they pay first. Then our editorial ops (RO) team reviews the ad copy and often finds issues — wrong abbreviations, missing contact details, banned words, wrong category, etc. The customer then has to redo their ad.

This tool aims to catch those issues **before payment**, at the compose step. It runs the ad through a rules engine and shows the customer what's wrong in real time.

But we can't switch it on until we're confident it agrees with the RO team at least **85% of the time** — otherwise we'd either block good ads or let bad ones through.

**Your job is to close that gap.** You look at cases where our engine and the RO team disagreed, figure out why, and either approve a new rule or flag that the existing rule needs fixing.

---

## The three modes

Every screen has a mode switcher: **Backtest → Shadow → Live**

| Mode | What it runs on | Customer sees it? |
|---|---|---|
| **Backtest** | ~71 historical ads that the RO team flagged | No |
| **Shadow** | New ads, daily, silently in the background | No |
| **Live** | Real-time at booking step 2 | Yes |

Right now only **Backtest** has data. Shadow starts once you've approved enough rules and we've run it for a few days. Live is the final unlock after sustained ≥85% alignment.

## The five screens

### 1. `/dashboard` — the scoreboard

Open this first every session. It shows:

- **Strict alignment %** — the number that matters. Formula: `(FULL_MATCH + BOTH_CLEAN) / total eligible`. Target ≥85%.
- **Partial-credit %** — includes partial overlaps. Nice to track but not the gate metric.
- **Active rules** — how many rules the engine is currently using.
- **Pending proposals** — rules the LLM drafted that haven't been reviewed yet.
- **Outcome breakdown** — the 8 buckets (explained below).

The 8 outcome buckets and what each means:

| Bucket | What happened | What to do |
|---|---|---|
| **FULL_MATCH** | We flagged it + RO flagged it, same reason | ✅ Engine is working. Spot-check a few. |
| **BOTH_CLEAN** | Neither we nor RO flagged it | ✅ Clean ad. Spot-check a few. |
| **RO_ONLY** | RO flagged it, we missed it | ⚠️ Highest priority — we need a rule for this |
| **WE_ONLY** | We flagged it, RO didn't | ⚠️ Possible false positive — rule too strict? |
| **PARTIAL_OVERLAP** | Both flagged it but for different reasons | 🔍 Partial credit. Check if our reason is close enough. |
| **NO_OVERLAP_BOTH_FLAGGED** | Both flagged it, completely different reasons | 🔍 Two separate issues in the same ad |
| **PENDING_RO_REVIEW** | Ad not yet reviewed by RO (too recent) | ⏳ Skip for now |
| **DATA_QUALITY** | Something wrong with the data (bad encoding, missing text, etc.) | 🗑️ Log it and skip |

### 2. `/proposals` — approve the rule library

**Start here on your first session.** There are 368 rule proposals sitting here, generated by Claude Haiku from the `cat_mes` and `sub_category_tips` tables. These are the starting rules — nothing fires until you approve them.

**How to work through proposals:**

Each card shows:
- The **rule name** and what it checks
- The **rule type** — e.g. `regex_ban` (pattern match), `word_count_max` (too long), `llm_semantic` (needs AI to judge)
- The **severity** — `hard` (would block the customer) or `soft` (would warn)
- The **target reason** — which RO category this rule addresses
- The **customer message** — what the customer would see if this rule fires
- The **pattern** — the actual check (click "Show pattern" to expand)

**Approve** if: the rule makes sense, the customer message is clear, the pattern looks correct.

**Reject** if: the rule is too vague, fires on things that aren't actually problems, or the customer message is confusing. Add a note so we can improve it.

**Edit before approving** (for the important ones): if the rule is mostly right but the customer message needs work, edit it directly in the rule detail page after approving.

**Suggested split of labour for first pass (2 people, ~1–2 hours):**
- Person 1: proposals 1–184 (cat_mes source)
- Person 2: proposals 185–368 (sub_category_tips source)

**What to prioritise:** rules targeting `ro_reason 10` (Edit Ad Matter) — that's 53 of our 71 backtest misses.

### 3. `/review` — the daily work queue

This is where you spend most of your time once backtest/shadow runs are loaded. Seven tabs, each for a different outcome.

**Priority order for each session:**

**Tab 1: RO_ONLY (Missed) — do this first, every time**

These are ads the RO team caught that we didn't. Highest learning value.

For each row:
- Read the ad text
- Read what the RO team flagged (shown as reason name + any notes)
- Ask: does a rule exist for this? If yes, is it disabled?
- Actions available:
  - **"Draft a rule"** — creates a proposal pre-filled with context from this ad. The best action when there's clearly a pattern to encode.
  - **"Mark as data quality"** — if the RO note makes no sense or the ad text is garbled.
  - **"Skip"** — if the miss was a one-off edge case not worth a rule.

**Tab 2: WE_ONLY (False positives?)**

These are ads we flagged that the RO team passed. We were either too strict, or the RO team missed something.

For each row:
- Read the ad, read what our rule flagged
- If the rule clearly over-fired: click "Rule too strict" — this records that the rule needs loosening
- If the RO team likely just missed it: click "RO missed" — this is a mark for us to track

**Tab 3: PARTIAL_OVERLAP**

Both flagged it but on slightly different things. Often means our rule is correct but targets the wrong reason code, or we're catching a symptom not the root cause.

For each row: decide if the partial catch is "close enough" (confirm) or needs rule adjustment.

**Tab 4: FULL_MATCH — spot-check only**

We got it right. Scan a few to make sure the rule isn't firing for the wrong reason even though the outcome was correct.

**Tab 5: BOTH_CLEAN — spot-check only**

Clean ads, nothing to do. Occasionally a truly problematic ad slips through both — if you see one, draft a rule.

### 4. `/rules` — the rule catalogue

Lists all active, proposed, and disabled rules. Use this to:

- **See how many times a rule has fired** across all backtest/shadow runs (fire count column). A rule with 0 fires might be too narrow or mis-scoped.
- **Enable/disable rules** — toggle without deleting. If a rule is causing too many false positives in the review queue, disable it here and investigate.
- **Edit rules** — click into a rule to change the name, customer message, severity, or pattern. Always test your change against a few real ads before re-enabling.

Rule types and what each means:

| Type | How it works |
|---|---|
| `regex_ban` | Blocks ads containing a forbidden pattern (e.g. phone numbers in certain categories) |
| `must_contain` | Requires the ad to include certain keywords or phrases |
| `word_count_max` | Ad is too long for this publication or category |
| `word_count_min` | Ad is too short |
| `language_only` | Ad must be in a specific script (e.g. Devanagari for Hindi newspapers) |
| `format_pattern` | Structural check (e.g. PAN number format, pincode format) |
| `category_match` | The category chosen doesn't match the ad content |
| `llm_semantic` | Needs AI to judge — for things that can't be expressed as a pattern |

Prefer deterministic types over `llm_semantic` when possible — they're faster, cheaper, and more predictable.

---

### 5. `/review/[id]` — single-ad detail

Click into any row from the review list to see the full picture for one ad:

- **Snapshot text** — the original ad text at the time of submission (from `ad_master_update`)
- **Current text** — the edited version (if the RO team asked the customer to fix it, this will be different)
- **Our findings** — which rules fired, the reason codes, latency, LLM cost for this ad
- **RO team section** — the forum tickets the ops team raised, their internal notes, which status codes the ad went through

Use this view when a review row doesn't make sense from the list — the full context usually clarifies it.

## How to audit if the engine is actually working

**Week 1 (after approving proposals):**
- Run the backtest: `npm run backtest -- --reset` (ask Sharad to do this)
- Open `/dashboard` — strict alignment should be > 0% now
- Open `/review` → RO_ONLY tab — should have fewer rows than the 71 baseline
- Gut check: do the rules that fired on FULL_MATCH ads look correct? Open 5–10 and read them.

**Week 2+ (shadow mode):**
- Dashboard alignment % should be climbing. If it's stalled, look at WE_ONLY (we're being too strict somewhere) and RO_ONLY (we're missing a category of issue).
- Per-reason recall (from backtest output) tells you which reason codes we're still missing. Focus new rule drafting there.
- If strict alignment is > 70% for a week with no regressions, we're on track for the ≥85% gate.

**Red flags to escalate to Sharad:**
- Alignment % drops after a rule is activated (new false positives)
- A `hard` severity rule fires on ads the RO team consistently passes (rule is too aggressive for hard-block)
- RO_ONLY count is growing faster than it's shrinking (shadow mode is finding new issue types we've never encoded)
- Any `DATA_QUALITY` bucket growing rapidly (upstream data issue)

## Practical tips

- **Start with `soft` severity** for new rules. Once you've seen them fire correctly in backtest/shadow, upgrade to `hard`.
- **`llm_semantic` rules are expensive** (~₹0.10–0.50 per ad). Use sparingly — only when a regex genuinely can't express the check.
- **The customer message matters a lot.** This is what a paying customer sees if we block them. It needs to be: specific (what's wrong), actionable (what to fix), and polite.
- **Scope rules tightly.** A rule with `category_scope: null` fires on all 20k+ category/publication combinations. If the rule is really only relevant to, say, matrimonial ads in Hindi newspapers, scope it.
- **The backtest corpus is small (71 ads).** Alignment numbers from backtest should be directionally informative but not taken as precise metrics. Shadow mode on fresh ads is the real signal.

## Glossary

| Term | Meaning |
|---|---|
| **RO team** | Editorial ops reviewers at releaseMyAd who manually review ads post-payment today |
| **ro_reason** | The reason code the RO team assigns when they flag an ad (e.g. reason 10 = "Edit Ad Matter") |
| **Finding** | One rule that fired on an ad |
| **Verdict** | The engine's overall decision: `pass`, `warn`, or `block` |
| **Proposal** | An LLM-drafted rule waiting for human approval |
| **Active rule** | An approved, enabled rule that the engine actually uses |
| **Alignment** | How closely our engine's decisions match the RO team's decisions |
| **Strict alignment** | (FULL_MATCH + BOTH_CLEAN) / total — the gate metric |
| **Backtest** | Running the engine on historical ads with known RO decisions |
| **Shadow mode** | Running the engine on live ads silently, comparing to RO decisions after the fact |
